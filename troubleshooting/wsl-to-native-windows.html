WSL2를 통째로 걷어내고 Windows 네이티브로 옮긴 날 — 삽질 7개와 삭제 직전에 발견한 것

WSL2를 통째로 걷어내고 Windows 네이티브로 옮긴 날 — 삽질 7개와 삭제 직전에 발견한 것

개인 프로젝트 전부를 WSL2(Ubuntu 24.04) 위에서 돌리다가, 2026년 8월 23일 하루에 Windows 네이티브로 전면 이전하고 WSL 배포판을 지웠습니다. AI 에이전트 CLI 세 개, node 프로젝트 네 개, 데몬 두 개, 작업 스케줄러 여섯 개. 이 글은 그날 밟은 것들의 기록입니다. 결론부터: 옮기는 건 반나절, 옮긴 걸 믿을 수 있게 만드는 데 나머지 반나절이 들었습니다.

왜 옮겼나

발단은 “굳이 WSL 써야 하나”라는 한 마디였습니다. 확인해 보니 Claude Code와 Codex CLI는 이미 Windows 네이티브로 설치돼 있었고, Gemini 쪽 CLI(agy)도 공식 네이티브 바이너리가 있었습니다. WSL은 관성으로 남아 있던 것이지 필요해서 남아 있던 게 아니었습니다.

WSL을 쓰면서 실제로 겪던 비용은 이랬습니다.

  • 부팅 직후 WSL 콜드스타트 창에서 스케줄러 작업이 무증상으로 죽음(종료코드 0xC000013A). 부팅 후 3~4분이면 실패, 9분이면 성공하는 패턴을 실측으로 잡아야 했습니다.
  • 스크립트마다 /mnt/c/...와 C:\... 경로가 섞여서, 어디서 실행하느냐에 따라 같은 파일이 다른 파일이 됨.
  • tmux 세션 지속성이라는 장점이 있었지만, Claude Code의 --continue가 같은 역할을 해줘서 포기해도 됐습니다.

여섯 단계로 옮겼다

단계대상핵심
0agy(Gemini CLI)네이티브 설치. WSL에서 쓰던 “OAuth + 429 폴백 래퍼” 패턴을 Python 래퍼 + .cmd로 그대로 이식
1PowerShell 단축 명령wsl.exe + tmux 래핑 제거, Set-Location + 네이티브 실행으로 단순화
2node 프로젝트 4개WSL 홈 ~/projects → Windows projects\
3로컬 대시보드Linux 전용 /proc 읽기를 psutil로 교체
4우편함 감시 데몬wsl.exe 호출 제거, 실행 파일을 shutil.which()로 찾고, GNU timeout 대신 자체 타이머
5Discord 브리지WSL 심볼릭링크였던 .venv를 네이티브 venv로
6작업 스케줄러 6종Action을 wsl.exe -d Ubuntu -- bash -c → Git Bash bash.exe -lc로, 스크립트 7개의 /mnt/c 하드코딩 정정

여기까지는 순조로웠습니다. 삽질은 각 단계 사이에 있었습니다.

삽질 1. rsync에서 .git을 뺐다

프로젝트를 복사할 때 “빌드 산출물 같은 건 빼자”는 마음으로 .git을 제외했습니다. 옮기고 나서야 네 개 중 두 개가 실제 git 저장소였고, 커밋 안 된 로컬 변경까지 들고 있었다는 걸 알았습니다. 다시 복사했습니다.

교훈: 옮기기 전에 git status부터. “폴더”라고 생각한 것이 “저장소”일 수 있습니다.

삽질 2. 이미 죽어 있던 것을 옮기면서 발견했다

로컬 대시보드의 프로세스 목록 API는 Linux 전용 /proc와 ss를 읽고 있었습니다. 네이티브 Windows에서는 진작부터 500 에러를 내며 조용히 죽어 있었는데, 화면 한 구석이라 아무도 몰랐습니다. 옮기다가 발견해서 psutil로 바꿨습니다.

이전 작업의 부수 효과 중 하나는 “그동안 안 보던 곳을 전부 한 번씩 본다”는 것입니다.

삽질 3. cp949

Windows 네이티브 Python은 콘솔과 파이프의 기본 인코딩이 cp949입니다. 한글을 print()하는 스크립트가 리다이렉트 중에도 UnicodeEncodeError로 죽었습니다. 파이프라인 감시 스크립트가 이걸로 크래시했고, 감시 스크립트가 죽으면 감시 대상이 죽어도 아무도 모릅니다.

해결은 한 줄이지만 모든 자식 프로세스에 전파되도록 최상단 스크립트에서 한 번만 걸었습니다.

삽질 4. 로그 경로가 깨지면 실패가 안 보인다

스케줄러 작업의 Action은 bash -lc "스크립트 >> 로그 2>&1" 형태입니다. 로그 경로가 틀리면 리다이렉트가 실패하면서 스크립트가 한 줄도 실행되지 않고 종료됩니다. 그런데 실패를 관측하는 장치가 바로 그 로그라서, 실패가 어디에도 남지 않습니다.

그래서 등록 직후 bash -c 'echo test >> <로그경로>'로 로그 파일 생성부터 확인하는 걸 규칙으로 박았습니다. PowerShell에서 >>가 든 명령을 테스트하면 PowerShell이 자기 리다이렉트로 먹어 버려 exit 0인데 파일은 안 생기는 함정이 있어, 검증은 반드시 실제 실행 형태(bash -c)로 합니다.

삽질 5. “메커니즘이 같으니 하나만 테스트”는 성립하지 않는다

스케줄러 작업 세 개가 같은 실행 경로를 공유합니다. 하나만 실사 발동해 보고 나머지는 “메커니즘이 같다”며 생략한 적이 있었는데, 인자(로그 경로)가 달라서 첫 실전 아침에 둘 다 죽었습니다. 이번엔 여섯 개 전부 한 번씩 발동시켰습니다. 그중 하나는 첫 시도에서 품질 게이트가 “출처 URL 없음”으로 결과를 정상 폐기했고, 재시도로 통과했습니다. 게이트가 일하는 걸 눈으로 본 셈입니다.

삽질 6. 데몬 중복 기동

우편함 감시 데몬을 옮기고 왕복 테스트를 하던 중 프로세스가 잠깐 두 개 떠 있는 걸 봤습니다. 원인은 그날 못 잡았고, 정리만 하고 며칠 관찰했습니다. 재발은 없었습니다. “원인 미확정, 관찰 중”이라고 적어 두는 것도 기록입니다. 나중에 같은 증상이 나면 이 줄이 첫 단서가 됩니다.

삭제 직전에 발견한 것

모든 검증이 끝나고 wsl --unregister를 치기 직전, 마지막으로 WSL 홈을 한 번 더 훑었습니다. ~/.ssh/에 개인키 두 개가 있었습니다. 원격 서버용 하나, 보류 중인 프로젝트용 하나. 자동화 스크립트 어디에도 경로가 박혀 있지 않아서 검색에는 안 잡혔고, 유일한 사본이었습니다.

네이티브 쪽 ~/.ssh/로 복사하고, 두 파일의 sha256을 원본과 대조해서 같은 걸 확인한 뒤에 삭제했습니다.

이게 이 글에서 가장 중요한 줄입니다. 이전 체크리스트는 “실행되는 것”만 따라갑니다. 실행되지 않는 것 — 키, 인증서, 로컬 설정 — 은 목록에 없어서 잊힙니다. 지우기 전에 홈 디렉터리를 ls -la로 한 번 더 보는 30초가 서버 접근권을 살렸습니다.

그 뒤

  • 네이티브 전환 후 3주, 스케줄러 6종은 전부 제 시간에 돌고 있습니다. 부팅 콜드스타트 실패는 사라졌습니다.
  • 대신 새 함정이 하나 생겼습니다. Windows에서 .cmd 래퍼로 실행하면 명령줄 한계가 8,191자라 긴 프롬프트가 “명령줄이 너무 깁니다”로 죽습니다. 이건 9월에 따로 잡았고 다음 삽질노트에 씁니다.

체크리스트로 남긴 것

  1. 옮기기 전 git status — 폴더가 아니라 저장소일 수 있다.
  2. 옮기면서 안 보던 화면을 전부 한 번씩 연다.
  3. Windows Python은 PYTHONIOENCODING=utf-8을 최상단에서 전파.
  4. 스케줄러 등록 직후 로그 파일 생성부터 확인, 실제 실행 형태로.
  5. N개 등록하면 N개 전부 발동.
  6. 원인 미확정 증상도 날짜와 함께 적는다.
  7. 지우기 전에 ls -la ~ — 실행되지 않는 파일(키·인증서)이 유일본일 수 있다.
